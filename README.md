# Messanger

Go-сервер мессенджера с chi, PostgreSQL, регистрацией и входом по JWT.
Версия Go указана в `go.mod`.

## Запуск

Создайте PostgreSQL-базу и передайте конфигурацию через окружение. Пример для PowerShell:

```powershell
$env:DATABASE_URL = 'postgres://messanger:messanger@localhost:5432/messanger?sslmode=disable'
$jwtKey = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($jwtKey)
$rng.Dispose()
$env:JWT_SECRET = [Convert]::ToBase64String($jwtKey)
go run ./cmd/server
```

`.env.example` содержит пример настроек; файл `.env` автоматически не загружается.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `DATABASE_URL` | Строка подключения PostgreSQL, включая параметры pgxpool | Обязательна |
| `HTTP_ADDR` | Адрес HTTP-сервера | `:8080` |
| `SHUTDOWN_TIMEOUT` | Время ожидания завершения HTTP-запросов | `10s` |
| `JWT_SECRET` | Случайный ключ подписи, минимум 32 байта без пробелов по краям | Обязателен |
| `JWT_TTL` | Срок действия JWT, от `1s` до `24h` | `1h` |

Сохраните сгенерированный `JWT_SECRET` в защищённой конфигурации для следующих
запусков. Все экземпляры сервера должны использовать один ключ; его замена
делает ранее выданные токены недействительными.

Перед открытием HTTP-порта сервер проверяет соединение с базой (таймаут 5 секунд)
и применяет все новые миграции. Ошибка подключения или миграции прерывает запуск.
`GET /healthz` возвращает 200, `GET /readyz` проверяет PostgreSQL и возвращает
200 или 503. Ctrl+C / SIGTERM останавливает HTTP-сервер, затем закрывается пул.

## Регистрация и вход

Оба метода принимают `Content-Type: application/json`; максимальный размер тела —
16 КиБ. Неизвестные JSON-поля и несколько JSON-значений в одном запросе отклоняются.
Для передачи пароля и JWT через внешнюю сеть используйте HTTPS.

`POST /auth/register`:

```json
{"name":"Алиса","login":"alice","password":"a long unique password","email":"alice@example.com"}
```

`name`, `login` и `password` обязательны, `email` необязателен. Имя содержит
1–250 символов после удаления пробелов по краям. Логин содержит 3–100 символов:
латинские буквы, цифры, `_`, `.`, `-`; первый символ — буква, цифра или `_`.
Пробелы по краям логина удаляются, регистр сохраняется: `Alice` и `alice` — разные
логины. Пароль содержит минимум 8 символов и максимум 1024 байта UTF-8; пробелы
пароля сохраняются. Email проверяется на формат и ограничен 100 символами.

Успешная регистрация возвращает `201` и поля `id`, `name`, `login`, `created_at`.
Повторный логин возвращает `409`, неверные данные — `400`. Уникальность логина
обеспечивается ограничением PostgreSQL, в том числе при одновременных запросах.

`POST /auth/login`:

```json
{"login":"alice","password":"a long unique password"}
```

Успешный вход возвращает `200`:

```json
{"access_token":"<JWT>","token_type":"Bearer","expires_at":"2026-10-19T13:00:00Z"}
```

Токен подписан HS256 и содержит `sub` (UUID пользователя), `iss` (`messanger`),
`aud` (`messanger-api`), `iat` и `exp`. В `internal/security` есть проверка подписи,
алгоритма, срока действия, издателя, аудитории и UUID. Для защищённых
маршрутов клиент передаёт токен в `Authorization: Bearer <JWT>`. Refresh-токены
и выход с отзывом токена в текущий API не входят; после истечения срока нужен
повторный вход.

Неверный пароль и неизвестный логин получают одинаковый `401`; неизвестный
логин также проходит проверку фиктивного хэша. Хэш, соль и внутренние ошибки
не возвращаются клиенту. Ответы авторизации имеют `Cache-Control: no-store`.
Ошибки возвращаются как `{"error":"..."}`. Неверный Content-Type возвращает `415`,
слишком большое тело — `413`, внутренняя ошибка — `500`.

Пароли хэшируются через `golang.org/x/crypto/argon2.IDKey`: Argon2id v19,
64 МиБ памяти, 3 прохода, параллелизм 4, случайная соль 16 байт, хэш 32 байта.
Параметры соответствуют второму варианту из
[документации Argon2id](https://pkg.go.dev/golang.org/x/crypto/argon2#IDKey).
В существующем `users.password` хранится PHC-строка с алгоритмом, параметрами,
солью и хэшем; `users.salt` содержит ту же соль для совместимости с текущей
схемой. Новая миграция не требуется. Проверка использует сравнение за постоянное
время и ограничивает параметры, прочитанные из хэша.

Одновременно выполняются максимум два хэширования на экземпляр сервера;
при занятых слотах возвращается `429` с `Retry-After: 1`. Это ограничивает
память Argon2id, но не является ограничением попыток входа для пользователя или IP.

## WebSocket

`GET /ws` открывает соединение только с действительным JWT из `/auth/login`.
Передайте `Authorization: Bearer <JWT>` в HTTP-запросе установки соединения.
Общее middleware `Authenticate` проверяет токен и передаёт UUID пользователя
обработчику через контекст запроса (`UserIDFromContext`). Проверка выполняется
до WebSocket upgrade: отсутствие токена, неверная подпись,
неверные claims и истёкший срок дают `401` с `WWW-Authenticate: Bearer`.
Токены в URL и cookies не принимаются. Внешние подключения должны использовать `wss://`.

После успешного upgrade (`101 Switching Protocols`) сервер отправляет:

```json
{"type":"connected","user_id":"<UUID из JWT>"}
```

Отправка сообщения в существующий разговор (текстовый JSON-кадр):

```json
{"type":"message.send","content":"Привет!","message_type":"text","client_message_id":"<UUID клиента>","conversation_id":"<UUID чата>","sender_id":"<UUID из JWT>"}
```

`sender_id` должен совпадать с JWT, отправитель должен быть текущим участником
разговора. `message_type` — строковое перечисление, сейчас поддерживается `text`.
`content` хранится в `BYTEA`, передаётся строкой UTF-8 без преобразования текста;
будущее шифрование потребует согласованного строкового представления шифротекста.
Создание разговоров и управление их участниками в этот WS-протокол не входят.

Одна транзакция увеличивает `conversations.count`, использует новое значение как
`messages.sequence`, сохраняет сообщение и событие `message.send` в `outbox`.
Ключ идемпотентности — `(sender_id, client_message_id)`. Точный повтор возвращает
исходное сообщение без изменения счётчика и outbox. Другой контент, тип или разговор
с тем же ключом даёт `idempotency_conflict`. Одновременные записи сериализуются
блокировками PostgreSQL, в том числе между экземплярами сервера.

После успешной фиксации отправитель получает:

```json
{"type":"message.accepted","message_id":"<UUID сервера>","client_message_id":"<UUID клиента>","conversation_id":"<UUID чата>","sequence":1}
```

Это подтверждение сохранения. При обработке события брокера `message.send`
сценарий `Messages.Consume` загружает сообщение и текущих участников из БД и
отправляет всем участникам, кроме отправителя, во все доступные локальные WS-сессии:

```json
{"type":"message.new","content":"Привет!","message_type":"text","message_id":"<UUID сервера>","conversation_id":"<UUID чата>","sender_id":"<UUID отправителя>"}
```

Успешная запись в сокет хотя бы одного получателя фиксирует первый `delivered_at`
и событие outbox `message.delivered` одной транзакцией. Постановка в очередь
не считается доставкой. Это общий статус сообщения, без отдельных дат по участникам.
При повторной обработке `message.new` может прийти повторно: клиент устраняет
дубликаты по `message_id`. Ошибки записи и переполненные очереди возвращаются
вызывающему обработчику для будущего повтора через брокер.

При обработке события брокера `message.delivered` онлайн-отправитель получает:

```json
{"type":"message.delivered","client_message_id":"<UUID клиента>"}
```

Прочтение клиент подтверждает серверными UUID сообщений (1–100 элементов):

```json
{"type":"message.readed","message_ids":["<UUID сервера>","<UUID другого сообщения>"]}
```

Читать можно чужие сообщения в разговорах, где пользователь сейчас состоит.
Проверка всего массива и запись выполняются атомарно: при недоступном или
неизвестном UUID весь запрос отклоняется. Дубликаты UUID в массиве объединяются.
Первое прочтение заполняет `read_at` и создаёт outbox `message.readed`; остальные
прочтения, включая других участников группы, сохраняют исходную дату и не создают
повторных событий. Если время доставки ещё неизвестно, прочтение также фиксирует
`delivered_at` и событие `message.delivered`.

После фиксации читателю возвращается
`{"type":"message.readed.accepted","message_ids":["<UUID сервера>"]}`.
При обработке события брокера `message.readed` онлайн-отправитель получает:

```json
{"type":"message.readed","client_message_id":"<UUID клиента>"}
```

Офлайн-отправителю подтверждения доставки/прочтения не рассылаются.
**Kafka, outbox worker и push пока TODO.** События сохраняются, обработчики
`Messages.Consume(ctx, event, ws)` готовы и проверены прямым вызовом в тестах.
Пока worker и Kafka не подключены, автоматической рассылки `message.new`,
`message.delivered` и `message.readed` нет. Отложенная доставка при переподключении
и маршрутизация к WS-сессиям других экземпляров сервера требуют будущей интеграции.
Worker должен публиковать события в одноимённые топики, отмечать `published_at`
после подтверждения брокера и обеспечивать повторы; потребители должны вызывать
сценарий на экземплярах с нужными WS-сессиями.

Ошибки имеют вид `{"type":"error","code":"..."}`: `invalid_message` — неверный
JSON, команда или данные; `forbidden` — чужой `sender_id`, отсутствие членства
или недоступные сообщения; `idempotency_conflict` — изменение данных при повторе;
`internal_error` — внутренняя ошибка без раскрытия деталей БД.
После ошибки можно отправить исправленное сообщение. Неизвестные поля отклоняются.
Текст должен содержать непробельные символы, не содержать NUL и занимать не более
4096 байт UTF-8; пробелы сохраняются.
Бинарные кадры отклоняются. Размер входящего кадра ограничен 16 КиБ, превышение
закрывает соединение с кодом `1009`. В каждом подключении очередь ограничена
64 событиями; заполненные очереди пропускаются при доставке в другие подключения.

Авторизация проверяется при установке соединения.
Кадры ping/pong и закрытия обрабатываются; сервер проверяет связь каждые 30 секунд
с таймаутом ответа 5 секунд. При остановке приложения соединения закрываются,
новые подключения отклоняются с `503`.

Браузерный `Origin` должен соответствовать хосту сервера; подключения без `Origin`
допускаются. Стандартный браузерный `WebSocket` не позволяет задать заголовок
`Authorization`: текущий контракт рассчитан на клиенты с поддержкой этого
заголовка. Для браузерного клиента потребуется отдельный механизм авторизации
соединения.

Реализация использует [github.com/coder/websocket](https://github.com/coder/websocket)
с поддержкой отмены через context и обработки управляющих кадров.

## Структура

- `cmd/server`: конфигурация журналирования, сигналы и запуск приложения.
- `internal/app`: создание зависимостей и управление их жизненным циклом.
- `internal/config`: чтение и проверка переменных окружения.
- `internal/transport/http`: маршруты chi и HTTP-обработчики.
- `internal/usecase`: регистрация, вход, сообщения и обработка событий брокера.
- `internal/security`: Argon2id, выпуск и проверка JWT.
- `internal/storage/postgres`: pgxpool, пользователи, сообщения и транзакционный outbox.
- `internal/domain`: доменные модели без зависимости от HTTP и PostgreSQL.
- `database/migrations`: SQL и встроенный запуск golang-migrate.

При добавлении сценариев собирайте репозитории и сервисы в `internal/app`,
размещая их реализации в соответствующих пакетах. Передавайте зависимости
обработчикам через конструкторы; интерфейсы определяйте у потребителей.

## Миграции

Добавляйте пары `NNNNNN_name.up.sql` / `NNNNNN_name.down.sql` в
`database/migrations`. Они встраиваются в бинарник: после добавления SQL сервер
нужно пересобрать. Рабочая директория при запуске значения не имеет.

golang-migrate хранит версию и признак незавершённой миграции в `schema_migrations`.
Повторный запуск пропускает применённые версии; параллельные запуски координируются
блокировкой PostgreSQL. Ожидание блокировки и выполнение SQL миграции ограничены
30 секундами каждое. Для совместимости с golang-migrate используется адаптер
`pgx/stdlib` поверх того же pgxpool.

Автоматического отката нет. При ошибке проверьте состояние схемы и устраните
причину до ручного восстановления версии: `dirty` не сбрасывается автоматически.
golang-migrate не добавляет транзакцию вокруг файла: используйте явные
`BEGIN` / `COMMIT`, когда миграция должна быть атомарной и её SQL это допускает.
Исходный `000001_init.down.sql` удаляет таблицы и данные.

Миграция `000002_message_receipts` добавляет в `messages` поля `delivered_at`
и `read_at` типа `TIMESTAMPTZ`: `NULL` означает отсутствие подтверждения доставки
или прочтения. У существующих сообщений оба значения остаются `NULL`.
Прочтение требует заполненного `delivered_at`, а `read_at` не может быть раньше
доставки. Это общий статус сообщения, без детализации по участникам группы.
Подтверждение прочтения должно записывать и время доставки, если оно ещё неизвестно.
Откат удаляет оба времени без возможности их восстановления из оставшейся таблицы.
Миграция совместима со старой версией сервера; перед откатом остановите код,
использующий новые поля. WebSocket и обработчики событий заполняют эти даты.

Миграция `000003_message_outbox` добавляет строковый `messages.message_type`
(существующие сообщения получают `text`) и таблицу `outbox` с JSONB payload,
типом события, ссылкой на сообщение и датами создания/публикации. Пара
`(message_id, event_type)` уникальна; индекс ожидающих публикации включает только
строки с `published_at IS NULL`. Up совместим со старой записью сообщений за счёт
значения типа по умолчанию. Down сохраняет сообщения и даты квитанций, но удаляет
тип и все события outbox без возможности восстановления; перед откатом остановите
использующую их версию приложения.

## Проверки

```text
go test ./...
go vet ./...
go test -race ./...
```

Интеграционный тест миграций запускается, когда задана
`MESSANGER_TEST_DATABASE_URL`. Нужны права `CREATEDB`: тест создаёт отдельную
базу со случайным именем, проверяет up, повторный запуск с сохранением данных,
down и повторный up, затем удаляет только свою базу.
При той же настройке запускается интеграционный тест репозитория пользователей:
он создаёт собственную базу, проверяет чтение/запись, необязательный email,
параметризацию SQL и конфликт двух одновременных регистраций.
Тесты сообщений используют тот же изолированный стенд: проверяют членство,
идемпотентность, конкурентную выдачу sequence, откат при ошибке outbox, атомарное
пакетное прочтение и единственность событий при конкурирующих квитанциях.
Проверки выполнены на PostgreSQL 17; версия целевой рабочей БД в репозитории не задана.
