# Messanger

Каркас Go-сервера с chi, PostgreSQL и pgxpool. Версия Go указана в `go.mod`.

## Запуск

Создайте PostgreSQL-базу и передайте конфигурацию через окружение. Пример для PowerShell:

```powershell
$env:DATABASE_URL = 'postgres://messanger:messanger@localhost:5432/messanger?sslmode=disable'
go run ./cmd/server
```

`.env.example` содержит пример настроек; файл `.env` автоматически не загружается.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `DATABASE_URL` | Строка подключения PostgreSQL, включая параметры pgxpool | Обязательна |
| `HTTP_ADDR` | Адрес HTTP-сервера | `:8080` |
| `SHUTDOWN_TIMEOUT` | Время ожидания завершения HTTP-запросов | `10s` |

Перед открытием HTTP-порта сервер проверяет соединение с базой (таймаут 5 секунд)
и применяет все новые миграции. Ошибка подключения или миграции прерывает запуск.
`GET /healthz` возвращает 200, `GET /readyz` проверяет PostgreSQL и возвращает
200 или 503. Ctrl+C / SIGTERM останавливает HTTP-сервер, затем закрывается пул.

## Структура

- `cmd/server`: конфигурация журналирования, сигналы и запуск приложения.
- `internal/app`: создание зависимостей и управление их жизненным циклом.
- `internal/config`: чтение и проверка переменных окружения.
- `internal/transport/http`: маршруты chi и HTTP-обработчики.
- `internal/storage/postgres`: создание и проверка pgxpool.
- `internal/domain`: доменные модели без зависимости от HTTP и PostgreSQL.
- `database/migrations`: SQL и встроенный запуск golang-migrate.

При добавлении сценариев собирайте репозитории и сервисы в `internal/app`,
размещая их реализации в соответствующих пакетах. Передавайте зависимости
обработчикам через конструкторы; интерфейсы определяйте у потребителей.

## Миграции

Добавляйте пары `NNNNNN_name.up.sql` / `NNNNNN_name.down.sql` в
`database/migrations`. Они встраиваются в бинарник: после добавления SQL сервер
нужно пересобрать. Рабочая директория при запуске значения не имеет.

golang-migrate хранит версию и признак незавершённой миграции в `schema_migrations`.
Повторный запуск пропускает применённые версии; параллельные запуски координируются
блокировкой PostgreSQL. Ожидание блокировки и выполнение SQL миграции ограничены
30 секундами каждое. Для совместимости с golang-migrate используется адаптер
`pgx/stdlib` поверх того же pgxpool.

Автоматического отката нет. При ошибке проверьте состояние схемы и устраните
причину до ручного восстановления версии: `dirty` не сбрасывается автоматически.
golang-migrate не добавляет транзакцию вокруг файла: используйте явные
`BEGIN` / `COMMIT`, когда миграция должна быть атомарной и её SQL это допускает.
Исходный `000001_init.down.sql` удаляет таблицы и данные.

## Проверки

```text
go test ./...
go vet ./...
go test -race ./...
```

Интеграционный тест миграций запускается, когда задана
`MESSANGER_TEST_DATABASE_URL`. Нужны права `CREATEDB`: тест создаёт отдельную
базу со случайным именем, проверяет up, повторный запуск с сохранением данных,
down и повторный up, затем удаляет только свою базу.
