# Red → Green → Refactor

Прочитай требуемое поведение, подходящие существующие тесты и точку изменения.
Выбери самый маленький законченный сценарий и доступный уровень проверки:
доменный тест, тест сценария приложения, HTTP-контракта или интеграционный тест БД.
Форма теста должна определяться наблюдаемым контрактом, а не будущим устройством кода.

## Red

1. Напиши один тест, демонстрирующий требуемое новое поведение или воспроизводящий ошибку. Для сложной задачи двигайся по небольшим сценариям последовательно.
2. Запусти целевой тест до изменения реализации и посмотри фактическую причину отказа.
3. Падение должно означать отсутствие нужного поведения. Ошибку синтаксиса теста, недоступную БД, сломанную фикстуру или отсутствие toolchain сначала устрани. Если новый контракт требует ещё не существующего Go-символа, допустим минимальный компилируемый каркас без реализации, после чего нужен наблюдаемый поведенческий Red.

Если тест уже зелёный, установи причину: поведение уже существует, тест не проверяет
нужное условие или сценарий ошибки выбран неверно. Не ломай реализацию специально
и не заявляй Red, которого не наблюдал.

## Green

Внеси минимальное полноценное изменение, достаточное для сценария. Запусти тот же
тест и подходящие ближайшие проверки. Не ослабляй утверждения и не подменяй
ожидаемый результат текущим, чтобы получить зелёный статус.
Если существующие тесты выявили регрессию, исправь её до следующего сценария.

Для ошибки начни с регрессионного теста. Для SQL, блокировок и изоляции используй
целевую СУБД: mock подтверждает взаимодействие, но не семантику PostgreSQL.
Для конкурентного поведения управляй пересечением операций через синхронизацию
и проверяй инвариант; time.Sleep не является достаточным доказательством.

## Refactor

Когда поведение зелёное, при необходимости убери дублирование и улучши границы
в пределах задачи. После изменения повтори затронутые тесты.
Не совмещай рефакторинг с незаявленным изменением контракта.
Для следующего поведения начни новый цикл Red.

## Достоверность проверки

- Записывай фактические команды, причины Red и результаты Green. Не выдавай написанный, но не исполненный тест за пройденный цикл.
- Если окружение не позволяет выполнить тест, устрани доступную причину без изменения выбранного стека. Если это требует недостающей информации или разрешения, явно обозначь ограничение и запроси только необходимое; не утверждай завершение TDD.
- Не меняй версию Go, зависимости или глобальное окружение только ради удобства тестирования без основания в задаче.
- Тестируй значимый результат и ошибки, а не частные имена функций, порядок внутренних вызовов или текст собственной реализации без контракта на них.
- Заверши подходящими проверками проекта; для конкурентных изменений добавь race-проверку при поддержке среды. Не повторяй уже прошедшие проверки без новых изменений или причины.

В результате кратко укажи реализованное поведение, наблюдавшийся Red, итоговый Green,
выполненный рефакторинг и проверки, которые не удалось исполнить.
