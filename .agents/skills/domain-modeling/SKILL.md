# Моделирование предметной области

Начни с пользовательских сценариев, терминов и уже подтверждённых правил.
Прочитай существующие сущности, операции и схему хранения. Различай текущую
реализацию, желаемое поведение и предположения; таблица не является готовой
доменной моделью только из-за совпадения названия.

## Сценарии и инварианты

- Для операции определи действующее лицо, вход, предусловия, изменения, результат и причины отказа. Правило должно быть выражено проверяемым примером.
- Выдели идентичность сущностей, семантику значений и допустимые переходы состояния. Value object полезен для собственного правила или значения, а не как обязательная обёртка любого поля.
- Разделяй формат транспортных данных и доменную допустимость. Правило, которое должно работать для нескольких адаптеров, не должно существовать только в HTTP-обработчике.
- Для изменения сущности предпочитай операции, сохраняющие инвариант, произвольным сеттерам. Конструкторы и методы возвращают понятную доменную ошибку при нарушении правила.
- Для мессенджера рассматривай по необходимости разговор, членство, сообщение и вложение: кто может действовать, когда доступ прекращается, чем задаются порядок и идемпотентность, кому принадлежит загрузка. Не определяй эти решения за пользователя, если они существенны и ещё не согласованы.
- Не предполагай, что каждому сценарию нужны роли владельца, удаление, редактирование или доменное событие: включай только требуемое поведение.

## Границы согласованности

Выбирай границу агрегата по инвариантам, которые должны сохраняться атомарно,
и цене конкурентной записи. Не загружай всю историю переписки в память ради
операции над одним сообщением и не создавай один агрегат на весь мессенджер.

Для каждого инварианта определи механизм обеспечения: доменная операция,
ограничение БД, транзакция или их сочетание. Проверка в памяти не обеспечивает
уникальность между процессами. Если правило охватывает несколько агрегатов,
явно выбери требуемую согласованность и обработку отказа; не обещай атомарность
для независимых сетевых операций.

Не вводи eventual consistency и компенсацию без требования, которое допускает
временное нарушение согласованности. Если нужны события, определи момент
возникновения, данные и гарантию доставки; публикация до Commit может объявить
несуществующее изменение.

## Модель в Go

Держи доменные правила независимыми от chi, SQL-драйверов и формата JSON.
Используй простые Go-типы и небольшие интерфейсы, где это обеспечивает нужную
границу. Не добавляй репозиторий на каждую таблицу или универсальный CRUD-слой
ради соответствия терминологии DDD. Простая модель допустима, пока она сохраняет
необходимые правила и позволяет их проверить.

Если меняется существующая модель, сопоставь её со схемой, API и сохранёнными
данными. Отдельно обозначь миграцию и совместимость; моделирование само по себе
не разрешает применять изменение к рабочей базе.

## Результат

Покажи краткий словарь, операции и инварианты, границы атомарности и примеры
допустимого/недопустимого поведения. Зафиксируй существенные открытые вопросы.
При порученной реализации добавь проверки правил и соответствующие ограничения
хранения; при задаче только на проектирование не генерируй сервер целиком.
