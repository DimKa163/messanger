# Проверка SQL-запросов

Сначала прочитай актуальные миграции в `database/migrations`, запрос и его Go-вызовы.
Определи СУБД, версию, драйвер, бизнес-инвариант и ожидаемую кардинальность результата.
Не считай совпадение синтаксиса достаточной проверкой корректности.

## Проверка по существу

- Значения передаются параметрами драйвера. Динамические имена столбцов, таблиц и направления сортировки выбираются из закрытого списка: параметры SQL не заменяют идентификаторы.
- Для чатов, участников, сообщений и медиа проследи проверку доступа от текущего пользователя до запрашиваемого объекта. UUID и факт аутентификации сами по себе доступ не предоставляют. Проверь путь после удаления участника и изменение членства между проверкой и записью.
- Сопоставь JOIN с уникальными ключами: нет ли размножения строк, потери строк из-за NULL или превращения LEFT JOIN в INNER JOIN условием WHERE. Сверь типы и nullable-значения со Scan и Go-структурами.
- Для сортировки и пагинации проверь устойчивый порядок с разрешением равенств и соответствующий курсор. Для истории переписки учитывай ключ разговора и порядок сообщений; не предполагай, что UUID отражает время.
- Для повторной отправки проверь согласованную область уникальности `client_message_id`, поведение при конфликте и проверку неизменности содержимого. Конкретную область уникальности определяет контракт приложения.
- Составная операция должна сохранять инвариант при частичном отказе и одновременном выполнении. Проверь изоляцию, условный UPDATE, блокировку или другой механизм атомарности. Для номера сообщения `MAX(sequence)+1` без синхронизации недостаточно; уникальный индекс обнаруживает конфликт, но требует определённой обработки повтора.
- Внутри транзакции все относящиеся к ней запросы выполняются через тот же Tx. Проверь обработку Commit, отмену через context, Rollback, RowsAffected, закрытие Rows и Rows.Err. Не держи транзакцию открытой на сетевой отправке или загрузке медиа без обоснования.
- Сопоставь индексы с WHERE, JOIN, ORDER BY и реальным объёмом данных. Учти порядок столбцов, селективность, уже существующие UNIQUE-индексы, N+1 и неограниченные выборки. Последовательное сканирование небольшой таблицы само по себе не ошибка.

## Подтверждение

Выбирай проверку по риску изменения: целевые Go-тесты, интеграционный тест на той же
СУБД или план запроса. Для SQL PostgreSQL тест на SQLite не подтверждает семантику
типов, блокировок и изоляции.

Начинай анализ плана с EXPLAIN без ANALYZE. EXPLAIN ANALYZE исполняет запрос,
включая изменения и вызываемые функции. Такие проверки выполняй в изолированной
тестовой базе с подходящими данными; Rollback не отменяет любые внешние эффекты
и, например, выдачу значений последовательности. Не измеряй производительность
на рабочей базе только потому, что запрошено ревью.

Если важна конкуренция, создай контролируемое пересечение двух операций и проверь
результат в базе. Проверка через Go race detector не заменяет эту проверку.

## Результат

Для каждого подтверждённого замечания укажи файл и строку, условие воспроизведения,
нарушенный инвариант, последствие и минимальное исправление. Отделяй ошибки от
предположений об объёме данных. Перечисли выполненные проверки и оставшиеся пробелы.
При задаче только на ревью не переписывай исходники.

Справка при необходимости: [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html),
[транзакции в Go](https://go.dev/doc/database/execute-transactions).
